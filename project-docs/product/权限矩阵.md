# WeKnora 权限矩阵

> 事实源：`internal/router/rbac.go` 守卫定义、`internal/middleware/*` 认证与判定链路、`internal/application/access/*` 资源级访问解析、`internal/types/*` 角色与能力位常量。
> 保真度：中高——配置与判定逻辑代码可读，**角色的业务职责称谓为推断**，已逐处标注待确认。

## 权限位清单

### 一个权限位长什么样

WeKnora 的"权限位"不是单一维度，而是四层复合结构，每次请求可能同时经过其中 2～4 层判定：

| 层 | 载体（字段结构） | 回答的问题 |
|---|---|---|
| ① 租户角色 TenantRole | `TenantMember{UserID, TenantID, Role, Status}`，`Role∈{owner,admin,contributor,viewer}`，`tenantRoleLevel` 映射为 40/30/20/10 的数值层级 | "我在这个租户里是什么身份？" |
| ② 平台标志位 | `User{IsSystemAdmin bool, CanAccessAllTenants bool}` —— 与租户角色正交，不随 `X-Tenant-ID` 切换而变化 | "我是不是平台运维/跨租户超级用户？" |
| ③ 资源所有权 | `CreatorLookup func(c *gin.Context) (creatorID string, err error)` —— 把 URL 上的 `:id` 解析成资源的创建者 user_id，再与调用者比较 | "这个具体资源是不是我创建的？" |
| ④ 组织共享 / KB 访问 | `KnowledgeBaseShare{KnowledgeBaseID, OrganizationID, SourceTenantID, Permission OrgMemberRole}`、`AgentShare{...}`、`OrganizationTenantMember{OrganizationID, TenantID, Role OrgMemberRole}` —— `OrgMemberRole∈{admin,editor,viewer}` | "我的租户能不能通过组织共享/共享智能体碰到这个别人的 KB？权限上限是多少？" |
| ⑤（正交的第五种，机器身份专用）API Key 能力位 | `TenantAPIKeyScope{FullAccess bool, KnowledgeBaseIDs []string, Capabilities []string}` | "这把 API Key 能调哪些端点、能碰哪些 KB？"（与①②③完全独立，JWT 的角色梯子对 API Key 主体直接短路） |

路由层再叠加一个"守卫方法"（`internal/router/rbac.go` 里 `rbacGuards` 的 25 个方法），把①～⑤组合成每条路由要挂的门禁。

### 完整清单

#### 1. 角色档位表（7 个角色常量）

| 标识 | 字面值 | 层级/数值 | 适用范围 | 说明 |
|---|---|---|---|---|
| `TenantRoleOwner` | `"owner"` | 40（最高） | 租户级 | 唯一可以改租户本身、管理租户 API Key、成员增删改、邀请、删除租户 |
| `TenantRoleAdmin` | `"admin"` | 30 | 租户级 | 管理租户基础设施与所有人的资源，越过 ownership 检查 |
| `TenantRoleContributor` | `"contributor"` | 20 | 租户级 | 可创建资源；只能编辑/删除"自己创建"的资源 |
| `TenantRoleViewer` | `"viewer"` | 10（最低） | 租户级 | 只读；`TenantRoleFromContext` 在角色缺失时的兜底默认值（fail-closed） |
| `OrgRoleAdmin` | `"admin"` | 3（组织内部权重，与 TenantRole 数值空间不通用） | 组织级（跨租户共享） | 管理组织本身与所有共享记录 |
| `OrgRoleEditor` | `"editor"` | 2 | 组织级 | 可编辑组织内共享给自己租户的 KB 内容 |
| `OrgRoleViewer` | `"viewer"` | 1 | 组织级 | 只读浏览共享 KB |

平台级另有两个**不属于角色枚举、以布尔标志位存在**的档位（不在 7 个角色常量之内，但是权限矩阵的一部分）：`User.IsSystemAdmin`（平台系统管理员）、`User.CanAccessAllTenants`（跨租户超级用户，需同时打开集群级开关 `cfg.Tenant.EnableCrossTenantAccess` 才生效）。

#### 2. 守卫方法表（`rbacGuards` 共 25 个方法）

`rbac.go` 的 25 个方法里，**21 个是真正做准入判定、返回 `gin.HandlerFunc` 挂在路由上的"守卫"**；另外 4 个（`ensureAPIKeyAuthorizer` / `apiKeyGroup` / `apiKeyRoute` / `assertAPIKeyPoliciesMatchRoutes`）是 API-Key 策略登记与启动期自检的基础设施方法，本身不对请求做准入判定，只是把 API-Key 策略写进 `APIKeyRouteAuthorizer` 这张表。下表只列 21 个真正的守卫，并按"被多少条路由使用"重新核对过（原始 `rbac_extract.json` 只统计了同一行内联出现的 `g.Viewer()` 等文本，漏掉了在 `r.Group("/sessions", g.Viewer())`、`r.Group("/memory", g.Viewer())` 等**组级挂载**的守卫，因此低估；下表已改为逐路由展开重新统计）：

| 守卫 | 判定逻辑（一句话） | 被多少条路由使用（重新核对后） |
|---|---|---|
| `Viewer()` | `caller.Role.HasPermission(Viewer)`，即租户角色 ≥ Viewer；跨租户超管与 API Key 主体直接放行 | 176 |
| `Admin()` | 角色 ≥ Admin | 115 |
| `Contributor()` | 角色 ≥ Contributor | 12 |
| `Owner()` | 角色 ≥ Owner | 15 |
| `AdminOrSystemAdmin()` | 角色 ≥ Admin **或** `IsSystemAdminFromContext(ctx)==true` | 3 |
| `SystemAdmin()` | `User.IsSystemAdmin==true`（JWT）；API Key 主体则要求 `scope.IsPlatform()==true` 且已通过对应 `apiKeyPlatform(...)` 能力校验；**始终强制**，不受 `EnableRBAC` 开关影响 | 18（均为 `/system/admin/*`，且是唯一在组级挂载、其余同组路由继承的守卫） |
| `OwnedKBOrAdmin()` | 资源有 `creator_id`：调用者是 KB 创建者 **或** 角色 ≥ Admin；API Key 主体跳过此检查（所有权是"人"的概念） | 22 |
| `OwnedKBOrAdminFromKbIDParam()` | 同上，但从 `:kbId`（而非 `:id`）解析 KB，供 `/initialization/*` 使用 | 2 |
| `OwnedAgentOrAdmin()` | Agent 创建者 或 Admin+；内置 Agent（`IsBuiltin=true`）creator 为空串 ⇒ 恒需 Admin+ | 5 |
| `OwnedKnowledgeKBOrAdmin()` | 用 `:id`（知识文档 id）反查其所属 KB 的 `CreatorID`，同款"创建者或 Admin+" | 7 |
| `OwnedChunkKBOrAdmin()` | 用 `:knowledge_id` 反查 KB 创建者 | 4 |
| `OwnedChunkKBOrAdminFromChunkID()` | 用 `:id`（chunk id）反查 knowledge_id 再反查 KB 创建者；仅 `DELETE /chunks/by-id/:id/questions` 使用 | 3 |
| `OwnedWikiKBOrAdmin()` | 用 `:kb_id` 直接反查 KB 创建者 | 11 |
| `CrossTenant()` | `cfg.Tenant.EnableCrossTenantAccess==true` **且** `User.CanAccessAllTenants==true`；平台 API Key 直接放行；**不受** `EnableRBAC` 影响（恒强制） | 2 |
| `PathTenantMatch()` | URL `:id` 必须等于当前会话的 `TenantID`；跨租户超管例外 | 20（组级挂载在 `/tenants/:id`，覆盖组内全部子路由） |
| `KBAccessRead(param)` | 走"自有 KB → 组织共享 → 共享 Agent 兜底只读"三段链路，要求有效 `OrgMemberRole ≥ Viewer`；**不受** `EnableRBAC` 影响（KB 边界隔离恒强制） | 26 |
| `KBAccessWrite(param)` | 同链路，要求 `OrgMemberRole ≥ Editor`（共享 Agent 兜底路径在此级别不生效） | 33 |
| `KBAccessReadFromKnowledgeIDParam(param)` | 先用 `:knowledge_id` 查父 KB，再走 `KBAccessRead` 同款链路 | 6 |
| `KBAccessWriteFromKnowledgeIDParam(param)` | 同上，Editor 门槛 | 12 |
| `KBAccessReadFromChunkIDParam(param)` | 用 chunk 的冗余字段 `KnowledgeBaseID` 反查 KB，再走 `KBAccessRead` | 1 |
| `KBAccessWriteFromChunkIDParam(param)` | 同上，Editor 门槛 | 3 |

角色-only 四件套（Viewer/Contributor/Admin/Owner）与 `AdminOrSystemAdmin` 受 `cfg.Tenant.EnableRBAC` 开关调制：关闭时只记警告日志、照常放行（"anyone in the tenant can edit anything"的历史兼容行为）；`SystemAdmin()`、`CrossTenant()`、`KBAccessRead/Write*` 系列**不受该开关影响，恒强制**——这是一个容易被忽视的不对称点。

平台能力位（通过 `apiKeyPlatform(...)` 直接传常量，仅 Platform 型 Key 可用，共 16 条路由）：`system_tenants_read/manage`、`system_settings_read/manage`、`system_runtime_read/manage`、`system_audit_read` —— 覆盖 `/tenants/all`、`/tenants/search`、POST `/tenants`、`/tenants/:id`（GET/PUT/DELETE）、`/system/admin/settings*`、`/system/admin/runtime/*`、`/system/admin/tenants/apply-default-storage-quota`、`/system/admin/audit-log`。

两个"元策略"（不是业务能力，是策略构造原语）：
- `apiKeyFullAccess()`：`RequireFullAccess:true`，几乎所有 18+7 个能力策略都以它为基座叠加——**353 条路由**（占全部声明了 API Key 策略的路由的绝大多数）都可以被一把 `FullAccess=true` 的 Key 访问。
- `apiKeyAny()`：完全不设门槛（`RequireFullAccess:false` 且无能力要求），任何有效 Key（哪怕是范围受限的 scoped key）都能过。只用了 **2 条路由**：`GET /auth/me`、`GET /system/capabilities`。

### 每个标志位是干什么的

**角色层级怎么比较**：`TenantRole.HasPermission(required)` 就是 `r.Level() >= required.Level()`，`tenantRoleLevel = {Owner:40, Admin:30, Contributor:20, Viewer:10}`，留有空档方便插入新角色。`OrgMemberRole.HasPermission` 用另一套独立的 `{admin:3, editor:2, viewer:1}` 映射，两套数值空间**互不通用**，不能跨类型比较（这是刻意设计：租户角色管"我在这个租户里能干什么"，组织角色管"我的租户通过共享能碰别人多少东西"）。

**能力位怎么叠加**：`apiKeyXxx(base)` 是"再挂一个可选通行证"的语义，不是收窄。例如 `apiKeyRetrieve(apiKeyIngest(apiKeyFullAccess()))` 最终策略是 `{RequireFullAccess:true, Capabilities:[retrieve, ingest]}`；`APIKeyRouteAuthorizer.authorize()` 的判定顺序是：
1. `scope.FullAccess==true` → 直接放行（能力列表完全不看）；
2. 否则遍历 `policy.Capabilities`，命中任意一个（OR 语义）→ 放行；
3. 否则若 `policy.RequireFullAccess==false` 且 `Capabilities` 为空（即 `apiKeyAny()`）→ 放行；
4. 否则拒绝。

也就是说嵌套是"并集"：full-access key **或者** 具备其中任一被列出能力的 scoped key，都能过。`RequireFullAccess` 这个字段名有误导性——它只在 `Capabilities` 为空时才真正意味着"必须 full-access"；一旦叠加了任何能力，`RequireFullAccess=true` 就形同虚设（因为能力匹配分支完全不检查这个字段）。KB 范围仍然由下游 `KBAccess*` 守卫和 `AuthorizeTenantAPIKeyKnowledgeBases` 单独约束，能力位从不放宽 KB allow-list。

**不规整之处（如实列出，不强行归纳）**：
- `PUT /knowledge-bases/:id/pin`（置顶/取消置顶 KB）JWT 侧只要 `Viewer()`，API Key 侧只需 `retrieve` 能力——一个"写"动作被归到了"读"能力档位，注释解释是"pin 状态是 per-user 偏好，不需要编辑权限"，但从能力位命名直觉看容易让人误判 **（待确认：产品侧是否认可"pin 属于 retrieve 语义"这一分类，还是应该单独设能力位）**。
- `POST /knowledge-bases/:id/hybrid-search` 与 `GET` 同款端点并存（注释明说 GET 是为了向后兼容保留），两者都挂 `Viewer()+KBAccessRead`，POST 却在 API Key 侧仍归为 `retrieve`（不是 `ingest`），与"POST 默认视为写"的直觉不符，但这里是刻意的（搜索本质是读）。
- `chunkRead.POST("/batch-download", ...)`、`faqRead.POST("/search", ...)`：POST 方法但 API Key 策略仍是 `retrieve`，同理是"方法动词不代表能力分类"的例子。
- `OwnedKBOrAdminFromKbIDParam` 与 `OwnedKBOrAdmin` 逻辑完全一样，只是解析的 URL 参数名不同（`:kbId` vs `:id`）——本质是同一个矩阵格子的两个实例，不是独立的权限语义。

## 权限位怎么和人绑在一起

### 关联链路

```
[维护端]                          [认证入口]                    [中间件解析]                         [Context 落点]                          [守卫读取]
TenantMember 表(角色)         →  Bearer JWT (Authorization)  → middleware.Auth→authenticateJWTUser  → types.CallerContextKey(Caller{TenantID,UserID,Role})
User.IsSystemAdmin/                                                → resolveTargetTenant→resolveTenantRole      types.TenantRoleContextKey            → RequireRole/RequireOwnershipOrRole
CanAccessAllTenants                                                                                   types.SystemAdminContextKey            → RequireSystemAdmin/IsCrossTenantSuperuser
TenantAPIKey 表(能力位/KB allow-list) → X-API-Key 头           → authenticateAPIKeyRequest             types.TenantAPIKeyScopeContextKey     → APIKeyRouteAuthorizer.Middleware()（先于业务守卫跑，默认拒绝未声明路由）
kb_shares / agent_shares /            (随 JWT/API Key 请求携带  → RequireKBAccess→access.ResolveKB      middleware.KBAccessContextKey          → 下游 handler 读 KBAccess.Permission
organization_tenant_members            的 :id/:kb_id 等 URL 参数)                                       + 改写 ctx 的执行租户(EffectiveTenantID)
```

补充三条旁路认证通道（各自独立签发 `authSession`/等价上下文，绕开常规 JWT/API-Key 判定，但落点仍是同一套 `types.Caller`/`Principal` 结构）：
- Embed 渠道：`middleware.EmbedAuth` 用 publish token 认证，附加固定 `TenantRoleViewer` + `PrincipalEmbedChannel`；
- 工作区 MCP Server：`middleware.MCPEndpointAuth` 用 Endpoint bearer token 认证，合成一个"机器用户"+`TenantAPIKeyScope`（复用 API Key 能力位模型），并**额外检查了 `tenant.Status`**（见下）；
- 短时能力 URL：`/r/:token` 完全不经过 `types.Caller`，直接用 `resource_access_grants.TokenHash+ExpiresAt+RevokedAt` 校验一次性/限时读权限，是与 RBAC 完全正交的第三种机制。

角色解析的兜底规则（`resolveTenantRole`，4 步优先级）：① 有效 `tenant_members` 行 → 用其角色；② `X-Tenant-ID` 跨租户切换 + `CanAccessAllTenants` → 临时授予 `Admin`（不落库）；③ 目标是自己的 home tenant 且该租户尚无任何活跃成员 → "孤儿空间自愈"，自动写一行 `Owner` 成员关系；④ 以上都不满足：`EnableRBAC=true` 时 403，`EnableRBAC=false` 时兜底放行为 `Admin`（历史兼容）。

### 关联方式判定

四层判定分别走不同的绑定方式，**是复合而非单一模型**：

- **① 租户角色 = 按用户直连一张关系表**：`tenant_members(user_id, tenant_id, role, status)`，一个用户在不同租户可以有不同角色，没有"部门/机构"概念。
- **② 平台标志位 = 按用户属性直连**：`users.is_system_admin` / `users.can_access_all_tenants` 两个布尔列，不经过任何角色表，直接挂在用户行上。
- **③ 资源所有权 = 按属性表达式**（"资源.creator_id == 调用者.user_id"），不是角色也不是部门，是一次性、每次请求都重新求值的属性比较。
- **④ 组织共享 = 按"组织-租户"关系表 + 属性上限表达式**：`organization_tenant_members(organization_id, tenant_id, role)` 是**按租户（不是按用户）**加入组织的（Plan 3 重构后，成员单位从"用户"上移到"租户/空间"，见 `OrganizationTenantMember` 注释），共享的实际生效权限 = `min(kb_shares.permission, organization_tenant_members.role, 若调用者租户角色是Viewer则再压到Viewer)` 三方取最小值（`kbshare.go:CheckTenantKBPermission` + `applyTenantRoleCap`）。
- **⑤ API Key 能力位 = 按凭证直连**：能力和 KB allow-list 直接刻在 `tenant_api_keys` 行上，与任何用户/角色都无关，是纯粹的"机器凭证属性"。

### 其他维度

- **组织（Organization）**：真正影响的只有"跨租户看到多少共享 KB/Agent、以什么权限上限"，通过 `organization_tenant_members.role` 参与 `MinOrgRole` 三方取最小值运算（`internal/application/service/kbshare.go:506-507`）。`Organization.RequireApproval`/`Searchable`/`MemberLimit`/`InviteCodeValidityDays` 这些字段**确实被读取**（分别驱动加入流程是否需审批、是否出现在可搜索列表、成员数上限校验、邀请码过期时间——均在 `organization.go` service 的 join/invite 相关函数中，已确认非死字段，但未逐函数在此展开）。
- **空间/租户（Tenant）**：`tenant_members.status` 只有 `active` 才被 `resolveTenantRole` 认可（`invited`/`suspended` 视为"无成员关系"）——**已在 `middleware/auth.go:762` 及 `middleware/access.go:100` 确认被读取，是真正生效的字段**。`Tenant.Status`（字符串，默认 `"active"`）声明在 `internal/types/tenant.go:94`，全仓库**只在 `internal/middleware/mcp_endpoint_auth.go:54` 一处被读取**（工作区 MCP Server 认证时判断是否为 `inactive`/`disabled`）；但写入侧全仓库搜索只发现 `internal/application/service/tenant.go:46` 把它硬编码为 `"active"`，`UpdateTenant` handler（`internal/handler/tenant.go:593-628`）明确用白名单只放行 `Name`/`Description`、**故意排除** `Status` 字段，也没有找到任何 SystemAdmin 端点会改写它——即该字段目前**声明了、也确实被读了（仅一处），但没有任何 HTTP 路径能把它置成非 active 值，因此这一处检查在当前代码状态下永远不会触发拒绝**。这是"只在个别地方读过，且触发条件当前不可达"的典型例子，已按要求全量搜索写入点后才下此结论。
- **KB 共享（kb_shares/agent_shares）**：真正影响"能不能碰这个 KB/Agent、以什么权限碰"（Read/Write 两档，`access.ResolveKB`）；不影响租户角色，也不影响 API Key 能力位。
- **`resource_access_grants` 表需要单独澄清**：它与 `kb_shares`/`agent_shares` **不是同一类机制**——不参与 RBAC 判定，是给 `/r/:token` 用的、跟具体某个 `StoredResource` 绑定的一次性/限时签名令牌（`TokenHash`+`ExpiresAt`+`RevokedAt`），本质上是"能力 URL"而非"角色/共享"体系的一部分。其中 `AccessScope` 字段（声明为 `"read"` 默认值）经全量搜索确认**只在写入时被设为字面量 `"read"`（`internal/application/service/resource.go:267,314`），从未在任何读取/判定路径被比较或分支**——是一个当前完全不生效（声明了但从未被消费）的字段，为未来支持写权限预留。

## 主体与权限位的对应关系

### 角色 × 操作矩阵

角色是层级累加的（高层级自动拥有低层级的一切权限），下表只列**该档位相对上一档新增**的能力，SystemAdmin 是独立于该梯子之外的平台维度：

| 角色档位 | 新增可执行操作类别 |
|---|---|
| **Viewer** | 浏览/搜索全部租户内 KB、Agent、Chunk、Wiki、FAQ、Tag 及模型/向量库/MCP/数据源/IM/Embed 等基础设施的列表与详情；发起知识问答/Agent 对话/检索；管理自己的 Session 与收藏；对自己可见（含通过共享 Agent 只读可见）的 KB 置顶/取消置顶；查看组织成员与共享列表；退出租户（`/tenants/:id/leave`） |
| **Contributor** | 创建新资源（KB、Agent、Session）；对**自己创建**的 KB / Agent / Knowledge 文档 / Chunk / Wiki 页 / FAQ / Tag 做增删改（含重新解析、移动、批量操作、下载原文件）；复制/拷贝 KB 与 Agent（副本归自己所有）；对同类他人资源仍只有只读表现 |
| **Admin** | 对**任何人**创建的 KB / Agent / Knowledge / Chunk / Wiki / FAQ / Tag 做增删改（越过所有权限制）；管理 Model / VectorStore / StorageBackend / MCPService / DataSource / WebSearchProvider / IMChannel / EmbedChannel / MCPEndpoint / SandboxConfig / Skill 目录 等租户基础设施的增删改与凭据；运行 Evaluation；创建/更新/删除 Organization、审批加入申请、邀请成员；分享/取消分享自己有权处理的 KB/Agent 到组织；设置共享 Agent 的全局禁用；查看租户审计日志；批量执行知识重解析/删除/移动等跨 KB 内容写操作（这几个 body-scoped 批量端点只挂 Contributor，实际由 handler 内部再判 KB 所有权，见下方"待确认"） |
| **Owner** | 修改租户本身（名称/描述）；管理租户 API Key 全生命周期；配置 API 主体模式（Direct/SignedToken）；租户成员增删改（add/update-role/remove）；租户邀请管理（create/revoke、生成邀请链接）；删除租户 |
| **SystemAdmin（平台级，独立维度）** | 提升/撤销其他 SystemAdmin；创建系统用户、重置任意用户密码；平台级 API Key 管理；平台系统设置读写；平台运行时任务队列查看与操作；批量套用默认存储配额；平台级审计日志；此外经 `AdminOrSystemAdmin()` 可在**任意租户**内维护内置模型（`PUT /models/:id`、模型凭据）而无需该租户的 Admin 身份 |

## 后端实际校验了哪些

- **后端硬校验（真正在 gin 中间件/handler 里拒绝请求）**：全部 21 个真正的角色/所有权/KB-Access 守卫（合计覆盖约 400+ 条路由挂点，含组级继承），加上 API-Key 网关对 371 条已声明策略路由的能力/KB-allow-list 校验，加上 `resolveTenantRole`/`IsTenantAccessible`/`IsCrossTenantSuperuser` 等租户可达性判定，都是**服务端强制**，前端 UI 隐藏按钮只是体验优化，绕过前端直接打 API 一样会被拒绝。
- **仅前端消费、后端未强校验或强校验范围明显小于声明范围的字段**：
  - `Tenant.Status`：声明存在、有一处后端读取（MCP Endpoint 认证），但因写入侧无任何入口能把它改成非 active，实质上是"死配置"（见上文"其他维度"）。
  - `ResourceAccessGrant.AccessScope`：声明存在，写入恒为 `"read"`，读取侧从未分支判断——纯前端/未来预留字段，当前**零后端校验**。
  - `User.IsActive`：**部分校验**——登录（`Login`/`OIDCCallback`）时检查，禁止已停用账号签发新 Token；但 `ValidateToken`（`internal/application/service/user.go:1222`，Auth 中间件每次请求都调用它）**不重新检查** `IsActive`，意味着一个账号被停用后，其此前签发、尚未过期/未被撤销的 JWT 仍可继续通过全部路由鉴权，直到该 Token 自然过期或被显式 Revoke。这是"声明了、也确实被读，但只在特定入口读，其余绝大多数请求路径不读"的字段，按要求已排查 `IsActive` 在仓库中的每一处读取点。
  - `AddMemberRequest`/`TenantMember.Role` 的数据库层默认值 `'contributor'`（`gorm:"...default:'contributor'"`）：只是列默认值兜底，实际角色始终由请求体显式指定或由自愈逻辑写死为 `owner`，未发现任何路径依赖这个 DB 默认值生效。

## 高风险发现

以下均为代码可证的观察，不含臆测：

1. **`apiKeyAny()` 策略只用了 2 条路由（`GET /auth/me`、`GET /system/capabilities`），但设计上它对任何有效 Key（包括被 KB allow-list 严格限定的 scoped key）完全放行、不检查任何能力位**——`APIKeyRouteAuthorizer.authorize` 里 `!policy.RequireFullAccess && len(policy.Capabilities)==0` 分支即返回 nil。当前用途本身低风险（自我身份、部署能力探测），但如果未来有人为图省事把新端点错误地挂上 `apiKeyAny()` 而不是具体能力位，会造成能力位体系被绕过。
2. **`APIKeyRoutePolicy{PlatformOnly:true}` 若未同时携带任何 `Capabilities`（即误用 `apiKeyPlatform()` 不传参），会导致该路由对所有 API Key（含平台 full-access 语义的场景）恒 403**——`authorize()` 中 `if policy.PlatformOnly && len(policy.Capabilities)==0 { return forbidden }` 先于 `scope.FullAccess` 判断执行。当前代码里所有 `apiKeyPlatform(...)` 调用都带了参数，未发现实际触发，但这是一个容易在后续新增路由时踩中的"看似放宽实则锁死"的坑。
3. **守卫选型不一致会被"静默放过"**：`跨 KB 批量端点`（`PUT /knowledge/tags`、`POST /knowledge/batch-reparse|batch-delete|folder|move`）只挂 `Contributor()`，**没有** `OwnedXxxOrAdmin` 或 `KBAccessWrite`，路由层完全没有对目标 KB 做归属/权限校验，依赖 handler/service 内部逐条记录判定。这与同模块其余端点统一挂 `OwnedKnowledgeKBOrAdmin`+`KBAccessWriteFromKnowledgeIDParam` 的模式明显不同，属于 rbac.go 注释里明确警示过的"最常见 RBAC bug 来源"模式（"Contributor everywhere" drift），建议人工确认 service 层是否确实补齐了等价校验。
4. **`EnableRBAC` 开关的不对称覆盖面**：关闭该开关会让角色/所有权四件套（Viewer/Contributor/Admin/Owner + `OwnedXxxOrAdmin`）整体降级为"记日志不拦截"，但 `KBAccessRead/Write*` 系列（跨租户 KB 边界）、`CrossTenant()`、`SystemAdmin()`、`PathTenantMatch()` 均**不受此开关影响、恒强制**。这是刻意设计（保护跨租户/跨空间边界不因灰度开关而破防），但也意味着"关掉 RBAC = 租户内人人平等"这句话不完全成立——运维需要理解开关的真实作用域。
5. **`GET /tenants`（`ListTenants`）在 JWT 侧没有挂任何角色守卫**（`RegisterTenantRoutes` 中该行只有 API-Key 策略 `apiKeyManageTenantSettings(apiKeyFullAccess())`，没有 `g.Viewer()`），任何通过全局 `Auth` 中间件的登录用户即可调用，权限完全依赖 handler 内部按调用者身份过滤返回集合。
6. **`/api/v1/local-browser/extension`、`/api/v1/local-browser/extension/authorize`、`/api/v1/local-browser/internal` 三个端点注册在全局 `Auth` 中间件之前，完全不经过 JWT/API-Key 认证**，依赖各自 handler（`BrowserSkillExtension`/`BrowserSkillAuthorize`/`BrowserSkillInternal`）内部的设备配对/签名校验；这与 Embed、IM 回调、Sandbox WS、`/r/:token`、预签名文件是同一类"自带鉴权"设计模式，但由于绕开了统一 Auth 层，其安全性完全依赖 `internal/browserskill` 包内部实现是否严谨（本次未深入审查该包，仅确认路由层确实绕过了标准认证）。
7. **SystemAdmin 分组里 8/18 条端点（人事与平台 Key 管理：promote/revoke/list/reset-password/create-user/api-keys CRUD）对 API Key 完全未声明策略**——即便是平台 full-access Key 也无法调用，只有 JWT 会话可用；这是偏保守的设计（好现象），但意味着"文档若声称平台 Key 可以做全部系统管理"与实现不符，需要以代码为准。

## 候选领域信号

**角色名 → 候选业务角色**（均为代码可证的权限效果推断，业务称谓本身待产品确认）：
- `TenantRoleOwner` → "空间主理人/创始成员"：唯一能处置空间存亡（删除租户）、财务/密钥类资产（API Key）、人事（成员增删改）的角色。
- `TenantRoleAdmin` → "空间管理员/运营管理员"：负责基础设施配置与内容治理，但不掌握空间生死权。
- `TenantRoleContributor` → "内容贡献者/知识运营人员"：能生产内容（建 KB/Agent），但边界严格收在"自己创建的东西"。
- `TenantRoleViewer` → "空间访客/只读协作者"。
- `OrgRoleAdmin/Editor/Viewer` → "跨空间协作组织"里的"组织管理员/协作编辑者/组织访客"，作用域仅限于组织间资源共享，与空间内角色是两套并行体系。
- `User.IsSystemAdmin` → "平台运维/客户成功工程师"一类不属于任何客户空间、只对平台基座负责的角色。
- API Key 能力位（`retrieve`/`ingest`/`chat`/`manage_*`）→ 对应"检索型集成""内容同步型集成""对话机器人集成""运维自动化集成"等不同类型的对接系统身份，是机器主体的"岗位画像"。

**资源分组 → 候选业务模块边界**：知识库内容域（KB/Knowledge/Chunk/FAQ/Tag/Wiki）、智能体域（Agent/AgentShare）、会话与对话域（Session/Chat/Message/Memory）、空间与组织协作域（Tenant/Auth/Organization/Invitation）、租户基础设施域（Model/VectorStore/StorageBackend/MCPService/DataSource/WebSearchProvider/WeKnoraCloud/SandboxConfig）、外部渠道接入域（IM/Embed/MCPEndpoint）、平台运营域（SystemAdmin）——这与 `internal/router/routes_*.go` 的物理文件切分基本一一对应，可作为未来做"业务模块 × 权限矩阵"文档的天然分区。
